# Agent 对话内交易充值功能 · 简洁需求文档（实现版 v1.6）

**日期**：2026-08-26
**类型**：需求文档（Implement-Ready）
**适用端**：PC Web + H5（移动浏览器 / 微信内置浏览器）
**支付渠道**：微信支付（**不含支付宝、不含 iOS IAP**）
**状态**：v1.6 全部决策闭环，待开发评审（含后台可配消耗比率 0.71x）

---

## 1. 目标与范围（一句话）
在 Agent 对话流内，让用户以「可控确认 + 微信支付」完成充值，按**后台可配比例**将金额换算为积分，并提供**银行级交易明细**；本期支持 **PC 端 + H5 端**、**微信单渠道**、**积分不过期**；**退款功能延后到后续版本（v1 不含）**。

**范围**：充值主流程、积分换算（可配比例，积分即 token）、微信支付（PC+H5）、交易明细、后台比例配置、埋点。
**非范围（v1 不做）**：支付宝、iOS IAP / 苹果内购、发票、邮箱账单、首充钩子活动、积分过期（已定不过期）、消耗规则细化调优（如分模型/分功能差异化单价）。详见 §9。

## 2. 端 × 渠道矩阵（本期关键约束）

| 端 | 微信支付 |
|----|----------|
| **PC（桌面浏览器）** | Native 扫码支付（页面出二维码，手机微信扫码） |
| **H5 · 微信内置浏览器** | JSAPI（后端 OAuth 取 openid，直接调起） |
| **H5 · 微信外浏览器** | MWEB（H5 支付，跳微信中间页拉起；**v1 全开**） |

> **实现要点**
> - `pay_launch` 时后端按 **端标识 + UA** 决定支付类型（PC→Native / H5微信内→JSAPI / H5微信外→MWEB）。
> - 订单 / 积分 / 明细 / 比例后台**两端共用**，仅前端交互与支付调起不同。
> - **渠道费率**：按微信实际类目费率核算（约 0.6% 量级，以签约类目为准），不含 iOS 苹果税。
> - **MWEB 接入注意（H5 微信外 v1 全开）**：① 商户平台需配置 H5 支付**授权域名/支付域名**；② 若手机未安装微信 App，MWEB 拉起失败，需兜底提示"请安装微信或在微信内打开"；③ H5 支付费率与类目限制以微信签约为准（部分类目不支持 H5 支付，需提前确认）。

## 4. 充值档位与积分换算

- **档位**：20 / 50 / 100 / 200 / 500（元），**后台可配置增删**，前端非硬编码。
- **换算规则**：`到账积分 = 充值金额 × 基础比例 + 赠送积分`。当前默认 `100元 → 110积分`（基础比例 1.0、赠送 10）。
- **积分不过期**：v1 充值所得积分永久有效（无到期消耗），明细"赠送/过期"类型本期仅保留字段占位，过期逻辑进 v2。
- **比例可配（R13）**：
  - 配置项：基础比例、赠送比例/额、生效范围（全局/分群/ab_group）、灰度比例（10% 起）。
  - 校验：写入即算 `预期积分 = 金额 × 配置比例`，与 `points_credit` 实际值比对，**达成率须 =100% (±0.5%)**，超界告警并定位异常配置。
  - 灰度：改比例先 10% 小流量验证到账链路，guardrail（支付成功率/退款率/投诉）恶化自动回滚。

### 积分消耗场景定义（Q5 闭环）
- **消耗出口**：用户积分主要用于 **Agent 对话 / 模型 token 消耗**——每次对话（尤其调用大模型生成回复）按 token 用量扣减积分。
- **扣减规则（v1 最小闭环）**：对话引擎在生成回复前向积分账户**预占/实际扣减**积分（输入 token + 输出 token × 单价系数）；扣减成功后 R8 消费记录落账（场景=对话轮次/模型/功能），积分余额实时更新。
- **与充值闭环**：充值→积分入账（R6）→对话消耗（R8）→余额对账（R9）形成完整账户生命周期；积分不过期，可长期累积。
- **退款关联（R16，本期不做）**：已用于对话/token 的额度视为"已消耗、不可退"；后续退款仅回滚该笔充值中**未消耗**部分对应的额度（本金+赠送按同比例）。
- **v2 扩展**：分模型/分功能差异化单价、超额对话专属档、赠送积分定向消耗顺序等规则细化。

### 积分即 Token · 计费换算方案（简化版 · 细化）
**核心（用户确认）**：取消"积分"与"token"两层换算——**账户余额 = token 额度，1 额度即 1 个 token 的购买力**。充值按"DeepSeek 成本等价 × 兑换率"入账；调用 DeepSeek 时按 API 实际返回的 token 数直接扣减。本期**退款不做**（延后）。

**1. 充值换算（后台可配 `exchange_rate`，默认 1.1）**
- `入账额度 = 充值金额 × exchange_rate`
- 100 元 → 110 额度（对齐"充 100 得 110、多送 10%"的原始需求）
- 额度购买力锚定 DeepSeek 采购价：**1 额度 ≈ 1 元 DeepSeek 购买力**（即 1 额度能买 1M 输入 token 或 0.5M 输出 token @ DeepSeek 价）

**2. 调用扣减（DeepSeek 实际返回 tokens × 可配消耗比率）**
- DeepSeek API 返回 `prompt_tokens` + `completion_tokens`
- `本次花费(元) = prompt_tokens × input_price + completion_tokens × output_price`（`input_price=¥1/1e6`、`output_price=¥2/1e6`，即 ÷1,000,000）
- `本次扣额度 = 本次花费(元) × consumption_ratio`（`consumption_ratio` **消耗比率**，后台可配，默认 **0.71**）
- 消耗比率含义：扣减按 API 真实 token 花费的 0.71 倍入账，即用户实际只承担 71% 的真实算力成本，其余 29% 由平台补贴；比率可调成 >1（用户承担多于真实成本、平台赚算力差价）或 <1（平台补贴）。
- 未来换更贵模型：扣减按该模型价算（`model_price` 后台可配），逻辑不变。

**3. 预占与结算**
- 对话前按"预估 max token × 预占系数(默认 1.2)"预占额度；生成后按实际 tokens 结算、多退少补
- 余额不足 → 预占失败 → 提示"额度不足，需充值 X 元"并闭环充值流程

**4. 实例（DeepSeek-V4-Flash · 2026-08 官方价 输入¥1/M、输出¥2/M，`consumption_ratio=0.71`）**
- 充 100 元 → 110 额度（元购买力）
- 一轮对话（800 in + 600 out）：`800×1/1e6 + 600×2/1e6` = **¥0.002** 真实花费 → 扣 `0.002 × 0.71` = **0.00142 额度**
- 110 额度 ÷ 0.00142 = **≈ 77,500 轮**
- 结论：DeepSeek 极便宜，100 元按成本等价**真能聊数万轮**——这是事实，非 bug；`consumption_ratio` 是平台调节"用户承担成本比例"的唯一旋钮（见 §5 / §7）。

**5. 体验权衡（由 `consumption_ratio` 统一承载，不影响 v1 开发）**
- 充值时用 `exchange_rate` 决定"入账多少"；调用时用 `consumption_ratio`（默认 0.71）决定"扣多少"，二者相互独立、后台皆可配，组合即平台毛利模型。
- **平台补贴模式（默认 0.71<1）**：用户仅承担真实算力的 71%，感知"超值"、利于转化；平台承担剩余 29%。
- **平台赚差价模式（比率 >1）**：如设 1.2，用户承担 120% 真实成本，平台赚算力差价；明细须透明标注"含平台服务费"。

**6. 配置项（R13 同层）**：`exchange_rate`（充值兑换率，默认 1.1）、`consumption_ratio`（消耗比率，默认 0.71）、`input_price`/`output_price`（各模型，元/1e6 token）、`preoccupy_ratio`（预占系数）、`balance_warn_threshold`（余额预警）。

**7. 退款**：本期不做，延后到后续版本。

**8. 与充值/明细闭环**
- 充值 → 额度入账（R6）→ 对话消耗（R8，场景=对话轮次/模型）→ 余额对账（R9）形成完整账户生命周期；额度不过期（Q1 已定）。
- R8 消费记录"消耗"填本次扣额度，并可附 prompt/completion token 数便于对账。

## 5. 支付接入方案（退款延后）

```
触发充值 → 选档 → 确认付款(R4/R5)
  → pay_launch(后端按 端+UA 选类型)
       PC            → Native 扫码
       H5·微信内     → JSAPI(后端OAuth取openid)
       H5·微信外     → MWEB(跳微信中间页拉起)
  → 微信回调(pay_callback: 成功/失败/取消)
  → points_credit(异步入账, R6≤3秒播报)
  → 明细落账(R7-R15)
```

**幂等与一致性**：支付回调与积分入账解耦；"支付成功但未到账"监控告警（延迟 > N 分钟即告警）；回调重试须幂等（order_id 去重）。
**中断挽回（R12）**：取消/被切走回到对话立即播报订单状态，提供"继续支付"入口；明确"未支付=未扣款"。

**退款流程（R16，延后到 v2，本期不实现）**：
```
用户/后台发起退款 → 校验状态(仅"成功→可用"可退)
  → 调微信退款API(原路退回)
  → 微信异步回调 → 积分冻结→回滚 → 明细标记"已退款"(R15)
  → 主动推送"退款已到账"
```
- 退款金额上限 = 该笔实付；退款后对应积分回滚（**Q5 闭环：对话/模型 token 已消耗积分不可退**，仅退未消耗部分对应的"本金+赠送"比例积分）。

## 6. 交易明细（精简字段与能力）

- **字段**：流水号(order_id 主键) / 微信 transaction_id(双向关联) / 时间 / 类型(充值·消费·退款·赠送·过期) / 金额(元) / 渠道(微信) / 积分变动(±) / 状态(成功·处理中·已退款) / 关联对话 / 赠送标记。
- **能力**：类型·时间·状态筛选；按天/按笔钻取(R17)；CSV/对账单导出（PC 优先，H5 v1 仅查看）；微信账单双向反查；关键节点主动推送(R18)；明细回链当时对话(R19)。
- **状态机**：充值成功→可用；退款中→冻结；已退款→回滚积分。

## 10. 决策闭环总览（全部 Q 已定）
> ✅ **Q5 积分消耗场景（已闭环）**：消耗出口 = **Agent 对话 / 模型 token 消耗**；v1 接入对话扣减额度最小闭环（§4 消耗场景定义），R8 消费记录场景=对话轮次/模型/功能；已消耗额度不可退（后续退款仅退未消耗部分）。
> ✅ **端补充（已闭环）**：H5 微信外 **MWEB v1 全开**（覆盖微信外 H5 流量，仅多一层跳转）；接入注意见 §2 实现要点。
> ✅ **Q6 汇率 A-B 默认方案（已闭环，影响 M3 R20）**：
> - **首个变量**：测"赠送比例上浮"——基础 100:100 不变，赠送 10→20，即对照组 100:110 / 实验组 100:120（对用户感知更正向、对成本冲击更可控，不动"本金"心智）。
> - **最小样本**：每组 **≥1000 笔支付成功**（约对应 ≥2000 名触发用户）；观察窗口 **14 天**（覆盖复充周期）。
> - **决策指标（看长期，不看短期转化）**：月复充率 + 积分成本率（积分对应服务成本 / 充值收入）；guardrail = 支付成功率 / 退款率 / 投诉率不显著恶化，否则自动回滚。
> - 前置：R14 `pay_launch` 已埋 `ab_group` 字段，可归因到漏斗各步。

> 全部闭环：⏸ 退款延后(v2) ✅ 不考虑iOS(按微信费率) ✅ 首充钩子不做 ✅ 渠道暂定微信(去支付宝) ✅ 积分不过期 ✅ Q5 消耗=对话/token ✅ MWEB v1 全开 ✅ Q6 汇率A-B默认方案

> 细化项进展：积分—Token 对照方案已简化为 §4（统一 token 额度，积分即 token）；微信费率实值仍留技术/配置期细化，退款回滚公式随退款需求延后。
