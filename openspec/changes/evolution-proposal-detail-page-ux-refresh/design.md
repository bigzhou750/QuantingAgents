## Context

See proposal.md - Why. 当前实现已经有提案详情页、验证结果、审批记录和发布按钮，但页面把原始 JSON 暴露得过重，读者需要自己拼接状态、指标和动作含义。

## Goals / Non-Goals

**Goals:**
- 把提案详情页改成面向决策的阅读顺序
- 降低 JSON 噪音，提升验证结论和审批状态的可读性
- 保持现有 API 和数据模型不变，优先通过前端展示层重组信息

**Non-Goals:**
- 不重做自进化后端状态机
- 不改变验证、审批或发布的业务语义
- 不在这个变更里引入新的后端接口

## Decisions

- 采用“摘要头部 + 分段信息区 + 详情展开”的结构，而不是继续堆叠描述列表和原始 JSON，因为该页的首要任务是帮助用户做决策，而不是浏览完整数据。
- 将枚举值映射为中文可读文案，并保留原值作为辅助信息，因为状态与触发类型是用户最先需要理解的内容。
- 将 `diff`、对比结果和审计信息拆成可独立阅读的模块，并为每块提供空态，避免不同阶段的数据缺失时页面失去解释能力。
- 保留原始 JSON 折叠区作为次级入口，而不是彻底移除，因为排障时仍然需要原始数据。
- 动作区采用状态感知控制，避免用户看到与当前阶段无关的按钮；与其依赖用户理解状态，不如让 UI 明确限制可执行动作。

## Risks / Trade-offs

- [信息抽象过度] → 通过折叠原文和保留原始 JSON 查看入口，给排障用户留回原始数据
- [前端重构扩大回归面] → 通过保留现有 API、组件分段改造和页面级测试降低风险
- [空态解释不足] → 为每个数据区块显式定义“未生成 / 未执行 / 无可用数据”三种状态

## Migration Plan

1. 先改页面结构和文案映射，保持 API 调用不变。
2. 再把 diff、verification、approval 三块拆成可复用展示区。
3. 最后补齐前端测试和浏览器验收，确认现有提案数据可以被正确解释。
