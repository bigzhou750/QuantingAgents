## Context

See proposal.md - Why. 当前自进化链路已有提案、验证、审批和发布，但它更像一条功能链，不像一条硬边界控制面：基线会在阶段间漂移，冷却窗口只在配置层存在，发布失败依赖补偿，反馈回流不自动，overlay 隔离也不够强。

## Goals / Non-Goals

**Goals:**
- 固定提案到发布之间的基线参考
- 将冷却窗口纳入实际去重与触发抑制
- 明确发布和回滚的失败边界
- 将 post-release 反馈自动转入后续控制流
- 收紧 overlay 隔离的 runtime 影响面

**Non-Goals:**
- 不重做整套自进化前端
- 不替换现有数据库技术栈
- 不在本变更中引入外部沙箱供应商

## Decisions

- 提案创建时就写入 baseline_artifact_version，并把它作为后续验证与发布的强约束，因为 baseline 漂移会让同一候选在不同阶段对比失真。
- 冷却窗口要进入 trigger 去重和 proposal 生成前置判断，而不是只存配置，因为只有前置拦截才能真正减少重复计算和重复发布。
- promote / rollback 继续允许补偿，但把补偿顺序和失败语义收紧为显式阶段，因为完全分布式原子性在文件系统 + Mongo 混合场景里成本高且脆弱。
- post-release observe 应该落到治理事件和后续候选上，而不是停留在查询返回，因为生产闭环需要“被观察到的风险”自动变成“可执行动作”。
- overlay 验证需要从注入级别向隔离级别推进，但实现上仍然保留与现有 runtime 的兼容路径，因为当前系统已经有可工作的 overlay 机制，目标是收紧边界而不是推倒重来。

## Risks / Trade-offs

- [更强的基线冻结会增加重提案频率] → 通过显式提示基线变化原因并支持重新触发，避免悄悄漂移
- [冷却去重过严可能压制有效修复] → 通过过期时间和明确的重复判定键控制误杀
- [发布边界收紧会增加实现复杂度] → 先统一阶段语义，再逐步增强原子性，不追求一次性全局事务
- [自动回流可能产生噪音] → 通过阈值、聚类和人工复核门槛降低误触发

## Migration Plan

1. 先让提案 baseline 冻结并在验证 / 发布中强校验。
2. 再把 cooldown 逻辑接入 trigger 去重和重复提案拦截。
3. 然后收紧 promote / rollback 的阶段边界和补偿语义。
4. 再把 post-release 反馈写入后续自动回流管道。
5. 最后调整 overlay 验证边界，保持 runtime 兼容的同时提高隔离强度。
