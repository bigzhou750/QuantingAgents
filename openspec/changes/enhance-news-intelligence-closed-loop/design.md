## Context

See proposal.md - Why.

现有新闻关注模块已经能保存关注记录、展示工作台、做简单持仓影响分析和模拟告警，但实现重点仍是 CRUD 与三档规则。近期验证暴露出两个问题：新闻源失败会被吞成 0 条，工作台和持仓影响页面没有形成“采集 → 分析 → 观察 → 告警 → 复盘”的研究闭环。

## Goals / Non-Goals

**Goals:**

- 让新闻模块在冷启动、空库、单源失败时仍能给出可诊断、可降级的结果。
- 让每条新闻、事件聚类和持仓影响都有结构化 Agent 分析入口。
- 让持仓新闻影响页面自动加载最新分析，并在后台刷新过期结果。
- 让用户可以从新闻分析直接生成观察任务，并在后续复盘验证判断质量。
- 让告警从“模拟记录”升级为可确认、可忽略、可转观察、可复盘的研究提醒。

**Non-Goals:**

- 不做自动交易、下单联动或仓位建议。
- 不承诺实时全网舆情覆盖；首版只保证多源降级和可解释覆盖状态。
- 不把 Agent 输出作为确定性预测；所有分析必须保留证据边界。
- 不在本 change 引入复杂知识图谱平台，先做轻量事件、实体和关系结构。

## Decisions

### 1. 新闻供给采用“聚合器 + 来源适配器 + 覆盖报告”

新增一个新闻聚合服务层，统一调用现有 `news_data_service`、股票新闻接口、公告源、市场新闻源和兜底搜索源。聚合结果不只返回新闻列表，还返回 coverage：

- `direct_count`: 直接命中标的新闻数量
- `indirect_count`: 行业、概念、上下游或市场新闻数量
- `source_statuses`: 每个来源的 success/empty/failed/rate_limited/auth_failed
- `fallback_steps`: 实际执行过的降级步骤
- `freshness`: 最新新闻时间和数据是否过期

替代方案是继续在页面分别调用各新闻接口，但这样无法统一降级、去重和解释为什么没有新闻。

### 2. 新闻源失败必须显式建模

来源适配器返回结果要区分成功空数据和异常失败。比如 AKShare 解析失败、网络失败、限流、字段变更都必须进入 `fetch_failures`，不能算作“成功 0 条”。这会让 UI 能显示“来源异常”而不是误导用户以为没有新闻。

### 3. 事件聚类先轻量规则，后续再升级

首版事件聚类使用标题相似度、URL、发布时间窗口、标的、关键词和来源合并同一事件，避免重复标题刷屏。暂不引入向量库或完整知识图谱；如果后续噪声仍高，再引入 embeddings 和实体关系图。

### 4. Agent 分析输出使用固定 schema

Agent prompt 不直接生成自由文本，而是要求返回结构化 JSON，再由后端校验字段并保存。建议 schema：

- `event_summary`
- `event_type`
- `impact_direction`
- `impact_strength`
- `time_horizon`
- `affected_industries`
- `affected_concepts`
- `upstream_downstream_paths`
- `direct_symbols`
- `indirect_symbols`
- `portfolio_hits`
- `impact_paths`
- `evidence_strength`
- `market_confirmation`
- `watch_indicators`
- `uncertainties`
- `non_advisory_note`

如果 JSON 校验失败，后端返回规则降级分析，并保存 Agent 失败原因。

### 5. 持仓影响分析改成“自动 + 缓存 + 后台刷新”

页面进入时先读最近一次分析结果。如果没有结果或超过新鲜度窗口，后端启动后台刷新，前端显示当前可用结果和刷新状态。手动按钮保留为“重新分析”，不再是唯一入口。

### 6. 闭环状态独立于告警投递

告警只是提醒，不等于闭环。新增观察任务和复盘记录：

```
新闻/事件
  ↓
Agent 影响分析
  ↓
持仓命中 / 告警
  ↓
观察任务
  ↓
1日/3日/7日复盘
  ↓
分析质量指标
```

告警可以转观察任务，观察任务可以复盘，复盘结果反向用于调阈值和降低噪声。

### 7. UI 按研究工作流重组

新闻关注下建议保留 4 个页面或标签：

- **关注工作台**：关注对象、相关新闻流、事件聚类、来源覆盖、分析入口。
- **持仓影响**：自动分析结果、多维评分、影响路径、观察任务入口。
- **事件分析**：单条/批量新闻的 Agent 分析详情。
- **闭环复盘**：告警确认、观察任务、复盘结果、闭环指标。

## Risks / Trade-offs

- [多源接入增加不稳定性] → 每个来源独立状态和超时，聚合器按来源隔离失败。
- [新闻量增加导致噪声] → 用事件聚类、来源权重、持仓相关性和用户忽略反馈降噪。
- [Agent 输出不稳定] → 固定 schema、prompt 版本、字段校验和规则降级。
- [自动分析增加成本和延迟] → 使用缓存、新鲜度窗口、后台刷新和按需批量分析。
- [间接影响容易过度推断] → 明确标注直接/间接、传导路径和证据强度。
- [用户误认为是交易建议] → API 和 UI 均保留非建议边界，拦截交易指令措辞。

## Migration Plan

1. 在不破坏现有 `/api/news-watch/*` 的前提下新增聚合接口和覆盖报告字段。
2. 将工作台新闻流切换到聚合服务，同时保留现有收集记录接口。
3. 新增 Agent 分析结果集合和 prompt/schema 版本记录。
4. 将持仓影响页面改为读取缓存结果并触发后台刷新。
5. 新增观察任务和复盘记录，接入告警状态流转。
6. 用真实 HTTP 验证新闻源、降级、Agent 分析、自动持仓分析和复盘闭环。
7. 若 Agent 或外部新闻源异常，回滚到规则聚合与来源覆盖展示，不影响收集记录读取。

## Open Questions

- 兜底搜索源首版使用哪个 provider，需要结合当前系统已有 API key 和合规边界确认。
- 观察任务是否复用现有任务中心，还是先在新闻闭环内维护轻量任务。
- 行业/概念映射首版复用现有股票基础信息，还是补充独立概念库。
