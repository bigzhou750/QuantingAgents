## Context

See proposal.md - Why.

当前系统已经具备新闻查询、新闻同步、自选股管理、持仓画像和股票详情页新闻区，但这些能力更像原子接口，缺少一个把“我关注什么”和“新闻影响我的仓位什么”串起来的产品层。

## Goals / Non-Goals

**Goals:**

- 让用户一键把股票或新闻放进个人关注工作台。
- 让用户看到最近关注对象对应的新闻流。
- 让用户看懂新闻对当前持仓的影响，而不是只看到新闻列表。
- 复用现有新闻数据、收藏和持仓数据。

**Non-Goals:**

- 不做自动交易或下单联动。
- 不做推送通知系统。
- 不承诺收益，不把新闻解释成交易建议。
- 不把新闻采集重做成新的抓取引擎。

## Decisions

### 1. 收集和分析分层

“收集”是轻动作：用户在股票详情、自选股或新闻流里一键加入关注工作台。  
“影响分析”是重一点的研究动作：系统再根据持仓、暴露度、新闻相关性和时间新鲜度生成解释。

### 2. 以现有数据源为基础，不重建新闻管道

现有 `/api/news-data`、`favorites` 和持仓画像已经能提供足够输入。新工作台只负责聚合和呈现，不复制新闻抓取逻辑。

### 3. 持仓影响分析按“暴露度 + 相关性 + 新鲜度”组织

分析结果应优先告诉用户：

- 哪些持仓被命中
- 哪些新闻最相关
- 影响方向是正面、负面还是中性
- 结论有多新、证据有多强

这比直接给“买卖建议”更适合新手，也更容易审查可靠性。

### 4. 影响等级使用三档，告警阈值由用户配置

影响分析结果统一分成低 / 中 / 高三档。用户可以在工作台里选择告警阈值：

- 选低：低/中/高都告警
- 选中：中/高都告警
- 选高：仅高等级告警

这让规则简单、可解释，也方便后续把模拟告警替换成真实投递。

### 5. 告警先做模拟投递，不接真实渠道

首版只记录“触发了什么、应发给谁、会走什么渠道”，不真正发送短信或微信消息。  
这样可以先验证触发逻辑、频控和文案，再单独接入外部服务。

### 6. 保持结果可追溯

每个收集动作和分析结果都应保留来源、时间和关联标的，方便用户回看“为什么这条新闻会出现在这里”。

### 7. 先做工作台，再做自动提醒

先验证用户是否愿意主动查看和筛选新闻。若后续确实需要提醒，再单独评估通知链路。

## Risks / Trade-offs

- [新闻过多导致噪声] → 用持仓相关性和收集来源做默认筛选。
- [把新闻影响误读成预测] → 输出只讲影响和风险，不讲收益承诺。
- [收藏和关注概念混淆] → 关注工作台只负责研究聚合，不替代自选股的资产管理语义。
- [数据源不一致] → 所有结果必须显示来源和时间戳，避免把缓存当成实时真相。
- [告警过于频繁] → 以等级阈值、去重和时间窗口控制告警量。
- [模拟告警被误认为真实通知] → 界面和日志必须明确标注“模拟”。

## Migration Plan

1. 先定义关注收集记录和持仓影响分析的输入输出。
2. 复用现有新闻查询和自选股接口做第一版聚合。
3. 增加工作台页面和结果页。
4. 增加分级配置和模拟告警记录。
5. 补前端交互和后端聚合测试。
6. 若分析质量不足，先退回到“新闻聚合 + 相关持仓标记”，不强行输出结论。

## Open Questions

- 关注工作台是否独立于自选股，还是与自选股共享一部分入口。
- 持仓影响分析首版是纯规则聚合，还是由 VibeAgent 补充解释文本。
- 新闻收集对象是否包含“股票”和“新闻条目”两种类型，还是先只收股票。
- 模拟告警记录是否要保留渠道模板，还是只保存触发摘要即可。
