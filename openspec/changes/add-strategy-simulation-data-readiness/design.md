## Context

系统已有 `stock_basic_info`、`market_quotes`、行情入库服务、数据源适配器和 APScheduler。个人投资助手当前选股依赖基础股票池和筛选服务，体检会读取指数数据，但数据质量与任务结果没有统一闸门。

## Goals / Non-Goals

**Goals:**

- 建立统一数据可用性服务，供策略广场、选股、体检、模拟指标使用。
- 通过定时任务和静默补数减少用户感知的数据同步动作。
- 实现第一阶段策略历史模拟摘要，不追求专业量化平台完整能力。
- 禁止数据不足时返回演示标的作为正式结果。

**Non-Goals:**

- 不实现分钟级高频回测。
- 不保证所有市场第一阶段全量覆盖，可优先 A股。
- 不把管理侧手动触发同步暴露给普通用户。

## Decisions

1. 数据可用性层放在 app 服务层
   - 理由：它需要编排 MongoDB、调度状态、个人投资任务和 API 响应，属于应用编排。
   - 替代方案：放入 `tradingagents/`，会把产品状态和用户任务语义带入核心库。

2. 定时更新为主，用户请求静默补数为辅
   - 理由：普通用户不应承担同步动作；静默补数用于处理少量缺口。
   - 替代方案：每次请求实时拉取全量数据，慢且容易触发限流。

3. 第一阶段历史模拟采用保守假设
   - 理由：先提供可信、可解释的摘要指标，避免承诺专业回测精度。
   - 替代方案：直接接入复杂回测引擎，会扩大范围并引入许可/数据口径风险。

## Risks / Trade-offs

- [Risk] 数据源权限或限流导致覆盖率不足 → Mitigation：备用数据源、状态记录和数据不足降级。
- [Risk] 历史模拟被用户误解为收益承诺 → Mitigation：所有指标标注“历史模拟，不代表未来”，并展示最大回撤和数据覆盖率。
- [Risk] 数据质量阈值过严导致结果少 → Mitigation：阈值配置化，并在结果中解释影响范围。

## Migration Plan

- 先新增数据可用性状态，不改变现有数据集合写入逻辑。
- 将个人投资助手任务逐步接入数据闸门。
- 策略模拟结果作为新集合或策略模板扩展字段保存。
- 回滚时可关闭数据闸门接入，保留原有数据更新任务。
